# 灰熊 SMS 美国接码

适用于当前商城的 Cloudflare Workers / D1 自营商品，不包含 Go / PostgreSQL 后端的适配。协议以灰熊公开的 [API 文档](https://grizzlysms.com/cn/docs) 为准，核对日期为 2026-10-17。

店主确认首批三个项目，均选择美国 `187`，不使用美国虚拟地区 `12`：

| 项目 | 上游服务代码 | 单次零售价 |
| --- | --- | --- |
| AI 聊天 | `dr` | ¥15.80 |
| Claude | `acz` | ¥19.80 |
| Google / Gmail | `go` | ¥25.80 |

目前先完成接码功能。店主尚未准备自动收款通道，因此正式接码销售保持关闭，未执行生产部署、真实取号或付款。三个商品模板带上述售价，不会自动写入生产商品或开售。

## 后台配置

1. 应用 `0049_grizzly_sms.sql` 和 `0050_grizzly_allocation_validation.sql`。
2. 进入「我的店铺 → 我的商店 → 商品发布」，点击“添加 AI 聊天”“添加 Claude”或“添加 Google / Gmail”。模板可分别编辑、定价、保存草稿或设为仅展示。
3. 添加商品图片，核对服务说明、售后范围、规格和上述零售价。选择供货来源“灰熊 SMS · 美国单次接码”。
4. 在遮蔽输入框填写灰熊 API Key，不发到聊天、不放入前端环境变量或源码。密钥通过现有 `PARTNER_AUTH_SECRET` 加密保存到 D1；旧订单保存独立的加密密钥与商品配置快照。
5. 填写单次美元采购上限和人民币成本核算汇率。美元上限作为 `maxPrice` 发送给灰熊；人民币最高采购成本按填写的汇率向上取整到分，售价和优惠后金额均不能低于此成本上限。成本汇率由店主填写，不是自动获取的实时汇率。
6. 点击“只读检查供货目录并保存配置”。只调用 `getBalance` 与指定美国项目的 `getPrices`，显示本次余额、报价与库存。没有购买或扣款。缺货、报价超过上限或余额不足时，保留草稿并核对账户。
7. 可以先选择“仅展示，暂不开售”。正式发布还要求可用的支付宝商户、验签公钥、付款回调域名，以及 `PAYMENT_CHECKOUT_ENABLED=true`、`GRIZZLY_SMS_ENABLED=true`。两个开关默认关闭；开启正式交易时 `ORDER_TESTING_ENABLED` 必须为 `false`。

当前新增订单的自动收款使用仓库已有的支付宝 RSA2 商户适配器。原 GPT 商品的供应商平台代收不能用于灰熊接码。若后续选择其他支付平台，须按该平台文档适配，不能把个人收款码当作自动到账凭据。查询和关闭已有支付订单不依赖当前销售开关。

## 买家流程与恢复

下单 → 本订单专属付款码 → 服务端验证付款渠道、订单号、金额与签名 → `getNumberV2` 获取美国手机号 → 买家在对应服务发送短信 → 订单每 5 秒查询 `getStatus` → 保存验证码并展示复制按钮 → `setStatus=6` 完成本次接码。

订单页面关闭时停止浏览器轮询，重新打开后继续查询；定时 Worker 每分钟核对尚未结束的原单。页面隐藏时暂停前端轮询，慢请求不会重叠。接码在本地分配成功后最多等待 20 分钟；到期先查最后一次短信，再尝试向灰熊取消。上游拒绝或返回结果不明时保留待核对状态，不假定取消成功。

- 客户点击“已付款”或伪造通知不能触发发号；接码商品没有人工声明付款或手填验证码交付入口。
- 分配前提交持久的采购尝试标记和订单租约。灰熊发号接口没有商家单号幂等参数，因此创建请求超时、重定向、响应丢失或损坏时，原订单转为待核对，不自动再买一个号码。
- 取得激活 ID 后先保存 ID、手机号及可核对的美元扣款记录。币种、美国地区、号码格式或成本检查不通过时暂停交付；异常号码不向买家展示。号码校验完成标记持久保存，进程在校验中断后也不能交付未核对号码。
- 验证码先保存，再结束上游激活；结束请求失败时仍保留已收到的验证码，由定时任务继续完成原激活。订单审计短暂失败后也能恢复同一验证码。
- 销售开关关闭后不再购买新号码，已知激活仍可查询、完成或取消。已付订单保持原项目、国家、密钥与上限快照。
- 手机号和验证码仅返回给原买家、经过邮箱验证找回订单的买家及已认证管理员。公开目录、普通日志和审计说明不保存密钥或验证码。

## 停止接码与退款

买家可点击“停止接码，保留订单”。系统先查询短信：同时到达的验证码优先保存；没有验证码时向上游发送 `setStatus=8`，只有收到明确取消确认才结束接码。停止接码和取消上游号码均不代表买家已经退款。

活动号码、发号结果不明、校验待处理或正在占用租约的订单不能直接进入退款；应用校验和数据库触发器共同阻止竞态。停止确认后，买家在原订单申请售后，再沿用既有的审核和实际退款流程。

结果不明的订单由店主在原订单核对灰熊账单、活动激活和客服记录。后台只向管理员显示上游激活编号和已知美元采购价；人工核对关闭必须填写处理说明及上游记录编号，并留下审计。已知激活需实际查询、确认取消；收到验证码的激活不能登记成未接码。未取得激活编号时依赖店主人工确认上游记录，没有自动推断或补购。关闭任务只解除进入退款审核的限制，不执行资金退款。

## 本机验证

```powershell
. ./scripts/local/env.ps1
& $NodeExe $NpmCli run build
$env:GPTIBO_LOCAL_VARIANT = 'grizzly'
& $NodeExe scripts/cloudflare/local-runtime.mjs
```

另一个项目终端执行：

```powershell
. ./scripts/local/env.ps1
& $NodeExe $NpmCli run test:cloudflare:grizzly-sms
```

独立环境为 `https://127.0.0.1:8791`，私有控制口为 `127.0.0.1:8794`；测试库、邮箱、临时文件、截图均位于被 Git 忽略的 `artifacts/local/`。复用项目已有的测试 TLS 证书和 D 盘依赖，浏览器只在本机测试上下文忽略证书校验。此环境的付款码、商户密钥、手机号、验证码及 API Key 全是模拟数据，不能用于真实业务。

Node 测试覆盖三个项目的签名付款通知到收码、伪造通知、金额篡改、买家隔离、重复通知、并发租约、发号超时、无号、余额不足、异常币种与地区、超价、过期、取消与收码竞态、密钥及商品快照、人工核对、审计失败及进程中断后的恢复。浏览器检查覆盖后台模板、三个商品和实际零售价、两次收码、一次取消、跨买家隔离及手机原订单找回。

验证记录：500 项 Node 测试、8 项真实本机 workerd / D1 浏览器检查通过；TypeScript、正式构建和静态检查通过，仅保留原有 5 条 Fast Refresh 警告与既有构建体积提示。测试没有调用真实灰熊账户，不能证明实际美国库存或目标网站接收成功率。真实灰熊 API Key、报价与账户余额、实际短信及正式收款仍需在接入后分别验证；本轮不自动发起付费测试。

回滚时保留这两个迁移、原订单与加密配置。停用新采购可先关闭 `GRIZZLY_SMS_ENABLED`，已有已知激活继续核对。已经产生订单后，不能回退到不认识这些订单的旧版前端或删除接码记录。

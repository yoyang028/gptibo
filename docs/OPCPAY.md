# 一人付评估与只读检查

2026-11-03 按当前官方文档、OpenAPI 和 `opcpay@0.3.4` 的 README、接入技能核对。用户确认的目标是**现有商城商品按订单收款**。

目前的一人付主要提供支付宝套餐购买入口、用户权益查询和次数/积分核销，不能直接接到本项目现有的自动按单收款交付流程。

## 为什么尚不能开放商城收款

| 商城需要的凭证或能力 | 一人付当前公开契约 |
| --- | --- |
| 创建绑定商城订单号、金额、收款商户的付款单 | `purchase` 创建某个用户、SKU 的购买入口，`READY` 不表示付款成功 |
| 服务端核验某一笔付款的订单、金额和交易号 | `purchaseQuery` 查询购买入口记录，`payment_status` 固定为 `NOT_AVAILABLE`；`transactionQuery` 尚未开放 |
| 付款成功通知 | 仅有权益与核销事件，没有 `payment.succeeded` |
| 原路退款与退款结果查询 | `refund`、`refundQuery` 尚未开放，接口返回 501 |
| 支付交易列表与账单对账 | `transactions`、`bills` 尚未开放，接口返回 501 |
| 稳定的已认证购买用户 | SDK 要求从服务端登录态取稳定内部 ID；商城现有游客 Cookie 和订单通知邮箱不等于登录账号 |

`access` 返回的是用户聚合权益，不能用余额增长推断某一笔订单成交。`consume` 成功是次数或积分核销凭证，也不包含本商城订单的实际收款金额及交易凭证。将商城改造成预付权益兑换属于不同业务模式，需另行确定计价、登录、退款和交付规则。

现有商城支付状态机要求核验订单号、金额、收款身份及支付流水，并把付款确认、订单流转和审计记录原子提交。它的支付宝官方适配器位于 `worker/payments/alipay.ts`，可作为按单支付的后续接入路径。

## 本次可运行的内容

- 安装并固定 `opcpay@0.3.4`，仅由服务端检查脚本导入。
- `npm run payments:opcpay:check` 只调用 `capabilities()` 和 `product()`，展示实际能力、收费模式、SKU、价格及数量，不写入数据库。
- 输出将“套餐购买可用”与“商城收款已接通”分开；安装 SDK 或只读查询成功均不会开启商城支付。
- 配置缺失时不发请求；错误仅输出固定代码和 HTTP 状态，不输出密钥、请求头、原始响应或 SDK 异常对象。
- 不设置演示套餐或价格。前端、支付通道注册及交付状态机保持现有行为。

## 配置及使用

若尚未开通，在[一人付官网](https://ai6666.com/opcpay/)完成“创建项目 → 扫码配置支付宝收费方式与套餐 → 申请 API Key”。第 2 步进入支付宝商品页面后，“授权信息”中显示“授权平台：碳基圈”。已有项目直接复用。

将密钥配置为运行检查脚本的**服务端环境变量 `opcpay_api_key`**，然后在仓库根目录执行：

```sh
npm run payments:opcpay:check
```

检查脚本不会自动加载 dotenv，也不读取远端 Worker Secret。`.dev.vars.example` 仅提供空占位；真实 `.dev.vars` 已被 Git 忽略，它不会自动进入上述 Node 进程。Workers 部署时秘密应存放于 Workers Secrets，不能使用前端 `VITE_` 变量、公开 `vars` 或 Git 文件保存。

退出码：`0` 表示两个只读查询及响应结构检查成功，`1` 表示查询或结构检查失败，`2` 表示缺少密钥。退出码 `0` 不代表商城支付适配已完成；以 `storefrontCollectionEnabled` 和交易契约为准。

本次未配置一人付 API Key，因而**尚未核验真实商户能力、套餐及收款**。已用模拟接口覆盖凭据缺失、实际套餐投影、异常与不完整返回、重定向策略及日志脱敏。本次没有创建购买入口或发起核销。

继续接现有商城收款时，应选择具有正式订单创建、交易查询和退款协议的通道；若一人付后续开放相应能力，应先取得完整接口契约和真实只读结果，再实现独立适配器，完成订单金额/商户匹配、重复通知、超时恢复、唯一交付及售后验证。

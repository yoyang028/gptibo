# 自营店铺与商品发布

本轮功能适用于仓库现有的 Cloudflare Workers / D1 后端。主后台的「我的店铺」直接复用 `StoresWorkspace`、商品排序定价和通知组件，使用独立的主店铺记录，不创建代理账号，也不依赖代理登录。原有代理账号及其售价、公告和排序仍分别保存。

## 店铺管理

进入主管理后台的「我的店铺」：

- 「我的商店 → 商店概览 → 编辑」修改店铺名称、品牌名称、Logo、网页标题、首页简介、联系方式与公告。
- 「商品售价」编辑已有套餐的售价与销售状态。已知供货价会显示；没有确认成本的商品显示「待核对」，不会把未知成本显示成已确认利润。
- 「优惠码」配置固定减金额、有效期、次数、单邮箱限制及适用商品。减免与下单在同一个数据库事务中预留，关闭未付款订单后释放使用次数。
- 「商品上下架与排序」管理原有商品和新发布的商品。隐藏商品同时阻止直接访问详情后下单；已有订单继续可查。
- 「商品订单」、订单收益、客户和访客页面使用现有工作台组件。平台代收的实际结算、提现仍在供应商平台完成，本店不生成虚拟的代理提现记录。
- 「账号设置 → 订单通知」可选开启完成通知，只通知开启后创建并完成的正式自营订单，默认关闭。

主管理员只管理当前根域名对应的主商城。域名页展示实际绑定状态；更换主域名需要同步 Cloudflare 和供货回调，不能仅修改一个显示地址。原代理工作台的多店、招募、上下级差价与域名收费属于代理业务，没有为自营店铺伪造这些关系或资金。

店铺营业状态、商品显示状态、套餐状态和对应供货销售开关都会参与下单校验。调整套餐售价不能替代环境中的供货开关。

## 发布自己的商品

「我的商店 → 商品发布 → 发布新商品」。每条配置对应一套规格和售价；选择同一个「前台商品分组」后，首页和后台排序合并成一个商品，详情页提供规格选择。各规格继续使用自己的订单编号、供货 SKU、售价和配置快照。

需要先展示介绍与价格时，选择「仅展示，暂不开售」。展示状态不要求已配置收款或已验证采购凭据，公开目录会返回介绍与价格，所有下单入口仍关闭。填写收款并检查供货后，再选择「发布商品」开放购买。草稿和已下架商品继续隐藏。

分组和展示状态的本机浏览器验收使用 `npm run test:cloudflare:grouped-products`，固定连接独立的 `https://127.0.0.1:8781` 模拟环境。检查首页合并卡片、详情规格与价格切换、手机布局、后台分组以及未开售商品不能下单；所有凭据和商品数据均为本机测试数据。

可先保存草稿；正式发布必须补全：

1. 名称、分类、短介绍、详细说明、商品图片、规格、计价单位、售价及库存。
2. 至少一项商品特点、一个交付步骤和一个常见问题。
3. 购买条件、交付说明和售后范围。
4. 收款名称、付款说明，以及 HTTPS 收款链接或收款二维码。
5. 使用 API 供货时，填写基础地址、商品编码、最高采购成本和服务端密钥，并通过只读目录检查。

前台复用商城的商品卡片、详情双栏、订单摘要、流程与 FAQ 样式。只接受文本内容和受限图片格式，不执行商品介绍里的 HTML 或脚本。客户填写的补充字段用于账号标识或需求；密码、Session 和 API 密钥不应进入这种普通下单字段。

详细说明支持按空行分段。需要区分接入方案等内容时，在段首单独写一行 `### 方案标题`，下一行填写该方案的说明；前台和预览会显示分节标题，其余内容仍按普通文本展示。服务特点、额外费用与售后边界、交付步骤、常见问题分别填写到对应字段，避免全部堆在详细说明里。费用说明可写“页面价格为一次技术服务费”，避免调价后正文仍保留旧金额。

库存 `-1` 表示不限量。有限库存创建订单时预留，客户或店主关闭未付款、未提交付款核对的订单时释放。商品编辑有版本检查，并发购买不会覆盖库存，旧订单保留当时的商品、收款和交付说明快照。

### 自有商品收款与人工交付

新增商品使用店主填写的收款方式：

1. 客户下单后核对收款方与金额，再提交付款交易号或备注。
2. 客户的「已付款」声明只进入待核对状态，不会把订单标成已到账。
3. 店主在订单详情核对自己的实际收款记录，填写处理说明并确认到账。
4. 人工商品由店主填写账号资料、卡密、领取链接或服务结果，确认交付后在原订单展示。
5. 售后沿用原有申请与审核流程。手动收款退款需要先实际退还，再登记真实退款流水；系统不会代替店主执行未知收款渠道的资金转账。

ChatGPT 的 Quefa 平台代收仍走原有专用流程。它不会自动成为任意自有商品的收款通道。这里的新增商品收款目前是人工核实；没有声称接通新的支付宝或微信商户自动验款。

### JSON v1 供货接口

这是新增商品支持的明确接口契约，不是任意 API 地址的自动识别器。其他供应商协议需依据其文档适配并重新验证。密钥通过服务器加密后保存在 D1，不进入公开目录、详情或买家订单。

只接受公开 HTTPS 基础地址，不允许 URL 账号密码、IP 地址、内网域名或 API 基础地址查询参数。请求使用 `Authorization: Bearer <服务器端密钥>`，拒绝跳转与过大响应。

`GET /products`：

```json
{"products":[{"product_code":"example-subscription","available":true}]}
```

店主确认实际到账后，才发送一次 `POST /orders`：

```json
{
  "merchant_order_no":"YMX-EXAMPLE",
  "product_code":"example-subscription",
  "max_cost_cents":500,
  "email":"buyer@example.com",
  "fields":{"account_email":"account@example.com"}
}
```

同时携带 `Idempotency-Key: YMX-EXAMPLE`。接口需要保证相同商家单号不重复采购。

下单与 `GET /orders/{编号}` 查询的响应：

```json
{
  "merchant_order_no":"YMX-EXAMPLE",
  "order_id":"supplier-order-example",
  "status":"success",
  "cost_cents":100,
  "delivery_content":"原订单的交付内容"
}
```

上游必须执行 `max_cost_cents` 的单笔采购上限，并在响应返回非负整数 `cost_cents`。商品售价与优惠后价格不能低于设定的采购上限；未确认成本或超限的响应不会交付成功，也不会自动再次采购。

`status` 只能为 `pending`、`success`、`failed`，成功时交付内容必填。需要支持按原商家单号查询，避免下单超时未取得上游编号时再次采购。取得上游编号后继续查询该编号。响应身份不匹配、未知状态与网络中断都不会被当成交付成功；创建结果未知时只查原单。失败订单由店主核对原单，不自动新建采购。

订单保留供货配置快照。轮换生产加密主密钥或变更上游接口前，需要处理或核对尚未结束的订单并保留恢复资料。

## 验证与发布

新增迁移为 `0045_owner_shop.sql`、`0046_owner_shop_leases.sql`。后者使用独立租约标识，防止同一毫秒内的并发请求重复取得采购或通知任务。

先构建并启动仓库的独立本机 Cloudflare 模拟环境，再执行：

```sh
npm run test:cloudflare:owner-shop
```

该脚本固定访问 `https://127.0.0.1:8771`，读取独立模拟邮箱及测试验证器，只向本机服务发起业务操作。其 JSON v1 供货由本机服务截获模拟；浏览器禁止打开外部支付和供货网址。结果和桌面、手机截图位于被 Git 忽略的 `artifacts/local/evidence/owner-shop/`。

本轮代码验证：432 项 Node 测试通过；原购买与售后链路的 13 项浏览器检查通过；新增主店铺、商品发布、人工收款交付、API 交付和手机页面的 9 项浏览器检查通过。浏览器业务检查使用真实本机 workerd / D1 和模拟供应商，未新增真实付款。构建与 TypeScript 检查通过；静态检查保留原有 5 条 Fast Refresh 警告，没有新增错误。

原先「云端验收、销售关闭」属于此前的发布阶段。店主已进一步授权开放 GPT 售卖；每次营业发布仍需重新读取供货目录、核对规格与实际售价。发布版本、生产开关、远程迁移和只读验收结果单独保存在私有发布记录。

真实商业验证与模拟验证分别记录：目录授权、接口查询、正式回调测试通知、未付款订单或付款码，都不能单独证明真实充值、退款与提现已经完成。

回滚时保留数据库与供货记录。自营商品产生真实订单后，读取端必须继续支持其商品编号与交付快照，不能直接回退到不识别这些订单的旧前端。

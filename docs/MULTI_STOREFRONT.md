# 两家营业店、预留店与代理工作台

自营店保留三个名额，目前营业的是 ScholAI 科研主题店和通用商店；另一个名额暂未开放。它们共用现有主后台、同一个数据库和同一个 App 页面模板。代理另有账号、工作台和专属前台。

已核对 [上游项目说明](https://github.com/CoolkHz/gptibo)、[原代理工作台](https://github.com/CoolkHz/gptibo/blob/main/src/partner/Partner.tsx) 和 [原路由](https://github.com/CoolkHz/gptibo/blob/main/src/Root.tsx)：原项目已经提供 `/partner` 工作台及共享前台。本次沿用这些组件，补齐当前 Cloudflare 后端的代理店铺接口，没有另做一套代理界面。上游 Go 后端仍保留原实现。

## GPT 下单、付款和回调

两家营业店共用已经修复 Session Token 提取及旧页面保护的 GPT 充值服务。创建订单先校验实际店铺和独立售价，再将所属店铺、成交金额和上游商品冻结到原订单。付款码请求、支付核验、充值任务及售后均沿用这笔订单。

回调使用主后台的统一 `/api/recharge/webhook` 地址，通过签名和上游订单编号定位订单，不依赖顾客从哪个店铺访问。重复通知只处理一次；通知只能唤醒权威查询，不能直接把订单标成已付款或已充值成功。通用店后续绑定新域名，也可继续沿用此统一回调地址。

`node scripts/sites/checkout-acceptance.mjs` 使用隔离的真实 workerd/D1、浏览器及签名模拟上游，覆盖两家店的独立售价、创建订单、付款码、付款回调、长 JSON 中 Session Token 提取、旧页面拦截、重复提交、充值成功回调、订单归属和预留店停售。它不使用正式凭据，不产生真实付款或充值。真实付费订单的最终自动交付结果仍需独立观察，不能用模拟验收或账号预检替代。

该验收复用原本地 Cloudflare 环境的测试证书；先完成现有本地初始化与 `npm run build`。测试数据和截图位于 `artifacts/sites/evidence/two-stores-checkout/`，验收结束会自动停止测试服务。

## 主后台操作

原有侧栏和页面结构保持不变，进入「我的店铺」：

- 商店概览显示三家店各自的订单数、收益和近 30 天访客，顶部汇总三家自营店。
- 「当前店铺」切换店铺；复制链接、预览、商品售价、商店订单、商品展示排序和访客趋势对应当前选择。
- 每行「编辑」修改当前店铺的名称、品牌、Logo、标题、介绍、联系方式、公告和营业状态。
- 「商品售价」独立保存该店价格和销售状态；供货成本仍由现有服务接入管理，售价不能低于已知成本。
- 「统一修改参数」先选择源店，再选目标店和同步字段。只有勾选的字段被复制；品牌、价格和其他字段不会顺带覆盖。
- 「账号设置 → 订单通知」跟随当前店铺；也可在统一修改中同步通知开关。
- 商品价格同步单独勾选「商品售价与销售状态」。确认前会提示覆盖目标店的差异价格。并发修改导致任一版本过期时，整批撤回并要求刷新。
- 商品资料、供应商配置、库存和履约继续统一管理；发布的新商品默认沿用平台价格，之后可在各店分别调整。已有店铺价格覆盖值会保留。
- 自营订单统一回到主后台，保留下单时的店铺、价格及商品快照；「商店订单」按店查询。订单收益总页仍沿用现有总览，不重做账务页面。
- 优惠码可选择自营店与商品组合，前台报价、创建订单与使用次数预留校验实际目标店铺。

## 代理操作

主后台「代理管理 → 开通代理」填写邮箱后生成账号及推广链接，代理通过邮件验证码登录原工作台。平台可以查看代理的店铺、订单、客户、访客和收益，设置供货价或停用账号。

当前 Cloudflare 后端支持每个代理的默认店铺：店铺形象、联系方式、公告、商品售价与上下架、商品排序、订单列表与详情、客户、访客和现有收益结算。代理收款账号与提现表单也使用同一账号体系。代理只能操作自己名下数据；管理员预览为只读。代理停售或平台停用会阻止新单，历史订单保留。

代理前台直接复用自营店的页面样式，按代理身份读取自己的售价及展示参数。代理商品销售范围仍由现有代理目录决定，不自动把尚未开放代理销售的自有商品或供应商权限下放。

上游 Go 后端包含代理多店、域名收费、招募等更多功能。本次未把这些未接通的 Cloudflare 功能伪装为可用；工作台根据后端能力显示入口。代理工单与订单邮件通知在当前 Cloudflare 实现中仍未启用。
